# Connected mode: what is not safe yet, ranked

Collected from stages 1 to 5 (read-only follower, tablets that write through the hub, safety fixes, offline page load, pairing). Ranked by how much harm it could do in a real kitchen times how likely it is. "Smallest fix" is the least work that removes or contains the risk; "Real test" is what must be observed on real tablets, a real network and a real service before anyone relies on it. Nothing here has been run on real hardware.

| # | Risk | Why it matters | Smallest fix | Real test must check |
|---|---|---|---|---|
| 1 | **Plain http on the building's network.** Tokens, access codes and the whole kitchen (customer names) travel unencrypted; anyone on the Wi-Fi can read them. | Pairing and tokens protect against the wrong screen, not against someone listening. A shared guest Wi-Fi makes it likely. | Use the hosted https address, or put https in front of a hub computer; show the owner a warning on the setup screen when the page is not https (except localhost); say it in the owner's guide. | Capture traffic from a second device on the same Wi-Fi: nothing readable. The tablet's browser shows the page as secure. |
| 2 | **The hub is one computer.** Power cut, sleep, update or crash stops the shared view for every screen. Emergency mode (queue, last known kitchen) exists but has only run in a test harness. | A busy service with all tablets in emergency mode is the real failure test. | Make the hub computer start on boot, never sleep, and not update itself during service; run a written drill. | Pull the hub's power and the router's power for 15 minutes in a busy hour: every tablet keeps taking orders and sounding warnings, catches up with no lost or doubled tap, and the cook sees the list of refused taps. |
| 3 | **Two tabs on one tablet.** The hub queue and saved copy are single device keys; two open tabs both act as writers with the same identity and can overwrite each other's queue. | Easy to do by accident (a second tab, a home-screen app plus the browser). | Allow one live hub client per device: take a lock (Web Locks or a BroadcastChannel claim) and show "already open in another tab" in the second. | Open the app twice on one tablet, tap in both, reload one: no lost or doubled tap. |
| 4 | **Replaying the record after an upgrade.** The hub rebuilds its state from a saved state plus a record of actions run through the engine. If a new engine version behaves differently, an old record can stop or diverge. | A nightly update that changes engine rules can silently change yesterday's history on restart. | Stamp the record with the engine's build version; on a stamp change, save a full state first and start a fresh record; refuse to replay across versions. | Restart the hub across an upgrade that changes a rule: the state before and after is identical. |
| 5 | **Fsync on every action.** An action is answered only after it is on disk. On a slow disk (SD card) every tap waits. | A board that feels slow is abandoned. | Measure; if slow, batch several actions into one disk write per few milliseconds (still answer after the write). | Tap-to-board time on the real hub hardware under a busy rush (target under 300 ms at the 95th percentile). |
| 6 | **Undo is single-step and strict.** In hub mode only your own last action, and only if nobody did anything after it. | Cooks will find it refused often in a busy kitchen and fix by hand; that is safe but annoying. | Keep. If it is a real pain, allow undo past other people's unrelated actions on different tickets. | Count refused undos over a real service and ask the cooks. |
| 7 | **Offline page load only over https or localhost.** On a plain http hub address service workers do not run, so a reload with the hub down shows nothing. | The emergency case is exactly a reload. | Same as #1: https. | Reload each tablet model with the hub off: the app opens. iPad Safari storage clean-up after days of non-use must be tried. |
| 8 | **A bad service worker on a tablet.** Guarded in several ways (checked page only, falls back to the network, `?nosw`, hub-side switch-off, reset button) but a worker bug plus a dead hub can only be cleared in the browser's site settings. | A tablet that will not open is a lost tablet during service. | Keep the guards; add a visible "Reset offline copy" in Settings (the call exists); keep one test tablet without it during a pilot. | Install, update and remove the worker on each tablet model; try `?nosw` and the reset button; clear site data. |
| 9 | **Reload offline with no saved copy.** A tablet that has never reached the hub, or whose saved copy was cleared, cannot take taps until it connects once. | A new tablet during an outage. | Tell the owner to open each tablet once on the hub; show a plain "not connected yet" note. | First visit after the hub is down. |
| 10 | **The saved copy of the kitchen is 2 to 15 seconds old.** After a reload offline, the last few seconds are missing until reconnect. | Small; the queue and the hub's order fix it on reconnect. | Keep; show "last known, from HH:MM". | Compare the shown kitchen with the hub after a reconnect. |
| 11 | **Admin key and token files.** Whoever can read the hub's data folder can pair and remove screens. Tokens cannot be rotated except by pairing again; a stolen tablet needs an owner to remove it. | Physical access to the hub computer or a lost tablet. | Document file permissions; add "remove all screens" and a rotate-admin-key command; make removing a lost tablet a one-line step in the owner's guide. | Remove a screen while it is mid-service: cut off at once; its queued taps are kept. |
| 12 | **Behind a reverse proxy every screen shares one address.** Per-address limits were useless until `SMOKEBOX_TRUST_PROXY=1` (reads the last X-Forwarded-For entry, only from this computer). | Pairing and access-code limits would lock everyone together or nobody. | Turn it on when a proxy is in front; confirm what the proxy sends. | Through the real Caddy: two different phones on mobile data get separate counters; a spoofed header from outside the proxy changes nothing. |
| 13 | **Pairing codes can be burned.** More than 30 wrong codes anywhere pauses pairing for ten minutes; a pest can keep the owner from adding a screen. | Annoying, not dangerous. | Owner makes a new code after the pause; consider a longer code for hosted hubs. | Try to guess codes from several machines; the owner can still pair afterwards. |
| 14 | **Hub writes only work from the hub's own page.** A page from another address cannot post actions (cross-site protection). | A tablet that opens a saved copy of the app file cannot join. | Keep (it is the protection); document it. Allow token-authenticated cross-origin writes only if needed. | Join from the page served by the hub, from the hosted address and from a home-screen shortcut. |
| 15 | **Whole state on the wire.** The old `/events` stream and snapshots send the whole kitchen; measured about 188 KB after 120 tickets, 12 MB cumulative for one follower. Fine on a local network, heavy on mobile data. The follower and tablets use the lighter action stream except at (re)connect. | A hosted hub over a weak mobile connection. | Send snapshots compressed (the proxy already gzips); trim old tickets from the snapshot. | A tablet on mobile data through a full day: data used, reconnect time. |
| 16 | **Seed limit and size.** A kitchen over 8 MB cannot be sent to a hub. | A big old kitchen. | Back up and trim old history before joining. | Join with a year of history. |
| 17 | **Clocks.** The hub's clock is the truth; tablets follow it. A tablet with a very wrong clock shows right elapsed times only after the first message. | Cooked-food timers across a daylight saving night. | Keep; test across the clock change. | Wrong device clock (minutes and an hour), and the daylight saving night. |
| 18 | **Owner-chosen names live on the device.** Station and menu-section names are not part of the shared kitchen, so a second screen may show the barbecue or neutral defaults. | Looks wrong, not dangerous. | Put the names into the hub's state. | Rename a station on the main tablet; check every screen. |
| 19 | **Version mismatch window.** A tablet with an old page keeps working until the next visit; a hub started with a minimum client version refuses it with plain words. | A hub upgrade mid-service. | Set the minimum client version only between services. | Upgrade the hub with tablets open. |
| 20 | **Pilot counts mix screens.** Pull and discard counts are for the whole kitchen, not per screen. | The pilot gate "pulls logged" needs a per-observer view. | Add the screen name to the report. | Compare the report with an observer's count per screen. |

## What a real-world test day should be

One service, an observer with the sheet in `docs/pilot-observer-sheet.md`, two tablets plus one follower screen: run the hub on the real machine or the hosted address, over the building's own Wi-Fi. Do items 1, 2, 3, 6, 7 and 12 on purpose (listen on the network, cut the power, open two tabs, undo in a rush, reload offline, go through the proxy), and record what the cooks said. Only after that should any owner be told Connected mode works.
