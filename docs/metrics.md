# Smokebox analytics: `SB.metrics` (src/js/40-metrics.js)

Pure functions of `(dataset, opts)`. No DOM, no clock at load, no randomness, nothing is written back. Every function is total: an empty, junk or single-ticket input returns a well-formed empty result (arrays empty, stats `null`, counts `0`), never `NaN`, never throws. The shapes below are the ones the chart code reads; they are also written as JSDoc above each function in the source.

## 1. Conventions (read these once)

| Topic | Rule |
|---|---|
| Dataset | `SB.store.dataset()` shape: `{tickets, events, batches, learned, menu, ingredients, settings, range:{from,to}}`. Missing parts are treated as empty; `menu` / `ingredients` fall back to `SB.config`. |
| Options | `opts = {from, to, channel, zone, includeVoided}`. `from`/`to` default to `dataset.range`. The range is half-open: a ticket created exactly at `from` is in, exactly at `to` is out. `channel` / `zone` of `'all'` or absent mean no filter. A zone filter keeps tickets with at least one item in that zone and counts only that zone's lines. |
| Function options | Some functions take extras in the same object: `bucketMin`, `fold`, `now` (queueLoad, paceIndex), `binSec`, `maxSec` (ticketHistogram), `minSamples` (calibration), `day`, `ing`, `openingG` (stockBurn, batchTimeline), `staticYield` (yieldComparison), `limit` (insights). |
| Units | Durations are **milliseconds** (`*Ms`) unless the name says `Sec`. Money is dollars. Weights are grams. `*Pct` fields are **fractions 0..1** (0.67 = 67 %), with one exception: `thermal()` returns `hotPct` / `chilledPct` on the SPEC 0..100 scale. Yields from `yieldComparison` are fractions. |
| Unknown is not zero | A value that cannot be known is `null` (no finished ticket, a line without a price, a batch without a weight). Real zeros are only counts and sums that really are zero. Rows with unknown values are skipped, not zero-filled. |
| Service day | A service day starts at `settings.service.dayStartHour` (default 4 am). A ticket's service date and hour come from its **createdAt**. 12:45 am belongs to the previous service date as hour **24.75** (bucket 24, label "12 am"); 3:59 am is hour 27; 4:00 am starts a new day at hour 4. The weekday of a ticket is the weekday of its service date. |
| Speed ticket | A ticket counts in speed statistics when it is `status:'expedited'`, has `expeditedAt >= createdAt`, and is not voided. A recalled ticket carries its latest `expeditedAt`; one that is currently recalled (active again) is not finished. |
| Voided | Voided tickets are excluded from every speed statistic and counted separately (`voids`). `includeVoided:true` widens only volume and money (`created`, `byDay.tickets`, revenue), never the speed counts. |
| Forced bumps | `ticket.forced` tickets stay in the speed statistics (the time is real) but are flagged (`summary.forced`) and excluded from plate sync, anatomy and the learner-style per-unit work times. |
| Thresholds | Per channel: `settings.channels` overrides, then `SB.config.channels`; an unknown channel falls back to the first configured channel. `totalMs >= warn` is `'warn'`, `totalMs >= breach` is `'breach'` (exactly at the boundary is the worse level). `onTimePct` = share with `totalMs < warn`. |
| Shared handles | `M.prepare(ds, opts)` builds the per-dataset context once. Pass the handle in place of the dataset to every function. Some results are cached and shared between calls on a handle: treat them as read-only. |
| "Now" | Nothing reads the clock, except `rangePresets` when it is called without a time. Functions that need "now" (`paceIndex`, `queueLoad` for lines still open, `compare` is range-based and does not) take `opts.now` (the store clock in the app). Without it they use the newest timestamp in the data. |
| Order | Arrays are ordered for charting: time ascending, config order for channels and stations, largest first for rankings (stated per function). |

### Calling pattern for a page

```js
const ds = SB.store.dataset({ sample: true });
const f = { from, to, channel: 'all', now: SB.store.now() };
const p = SB.metrics.prepare(ds, f);                 // one pass over the tickets; same handle if called again with the same ds + f
const s = SB.metrics.summary(p), hours = SB.metrics.byHour(p), cards = SB.metrics.insights(p);
```

`prepare()` treats the dataset as an immutable snapshot (the engine never edits a state in place, so `SB.store.dataset()` is one). If you edit a dataset in place (a test, a script) use a fresh object or call `M.unprepare(ds)`.

## 2. Function table

Formula notes: `p(x)` is the linear-interpolation percentile (the same as `SB.util.percentile`); `idx = p/100 * (n-1)`, value = `v[lo] + (v[hi]-v[lo]) * (idx-lo)`. Example values come from three tickets: T1 dine-in (brisket 1/2 lb fired 0 started 30 done 200, mac fired 60 done 240, bumped 270 s), T2 takeout (brisket 1/2 lb fired 10 started 40 done 100, slaw fired 0 done 90, bumped 130 s after its creation), T3 a one-item drive-thru ticket that took 600 s.

## 3. Insight rules

`insights()` runs every rule in a `try/catch` (a rule that throws is skipped), drops the ones that return `null`, sorts by `importance` (descending, then id), and returns at most 8. Each finding has a stable `id`, a `tone`, a one-line `title`, a `body` that quotes the real numbers, and an optional `metric`. A rule needs a minimum sample before it speaks; none speaks on an empty or five-ticket dataset.

| id | Says (tone) | Fires when (guard) |
|---|---|---|

## 4. Performance

5000 tickets and 40,000 events: `summary + byHour + byWeekdayHour + insights` takes roughly 170-250 ms cold when each call builds its own context (first run in a fresh Node process, after a small warm-up slice; the spread is machine load), about 60 ms once the JIT is warm, and roughly 115-145 ms cold through one `prepare()` handle. The test (`test/metrics.test.mjs`, "performance") judges the best of up to five attempts on fresh dataset copies because a shared 2-core VM is noisy, and prints the first (cold) reading too. The cost is dominated by interpreter and tier-up time of the per-ticket loops, not by any algorithmic hot spot; every metric is O(tickets + events) apart from one native typed-array sort per statistic.

## 5. Known gaps

* Per-unit work times divide by the pacing quantity factor, so a line of qty 4 is treated as 2.2 units of work; real kitchens may scale differently.
* `queueLoad` rebuilds load from fire and done stamps, so a line that was never marked done runs to `now` and is capped at 12 h.
* `stockBurn` for non-TCS ingredients starts from par when no opening count is given; `openingAssumed` says so.
* Insight wording is English only and built from templates; thresholds are constants in the source, not settings.
* `compare("today", "yesterday")` compares a possibly partial day with a full one (counts differ, medians stay fair).
