# Smokebox findings

Every row is something that went wrong (or was deliberately changed) while building, what fixed it, and the test that now guards it. Same format as Pitcall's `findings.md`: `# | what went wrong | fix | test`.

## Engine and store

| # | What went wrong | Fix | Test |
|---|---|---|---|
| F-E1 | The research report measures "below 135 F for more than 2 h" from the moment the food was pulled from heat. A pan can sit in the cabinet reading 140 F for an hour, drop to 130 F, and the report's clock would already say 1 h into the 2 h window, even though the food has only been out of range for minutes. That is a deliberate deviation, not a bug. | The gate clock runs from the first out-of-range reading (`outSince`) and resets when a reading is back in range. The deviation is written in the Z spec and shown in the Safety help text. | `engine.unit.test.mjs` gate tests (out of range, back in range, discard) |
| F-E2 | A flat event log slowed every action once it passed about 16,000 events (the 14-day sample alone is bigger). | The log keeps a recent window in state and moves older events into archive chunks; `allEvents(state)` stitches them back for reports. | `engine.soak.test.mjs` (long soak), `store.test.mjs` (dataset) |
| F-E3 | Undoing a bump or void left items that were already due hidden until the next tick (fuzz seed 20261017, sequence 37, step 10). The ticket was active again but its queued items still thought they were waiting. | When a ticket becomes active again, due queued items fire at once (`firedAt = now`, marked `late: true`). | `engine.fuzz.test.mjs` (seeded replay) |
| F-E4 | Undoing the discard of an empty expired pan discarded it again immediately (seed 777, sequence 21, step 103). | The "frozen when empty" rule moved into `refreshBatch`, so every path through the engine applies it. | `engine.fuzz.test.mjs` (seeded replay) |
| F-E5 | The store's quota fallback had only two trim levels. A full browser store could still fail to save. | Adaptive halving through `prune`, with the ledger kept balanced; a failed save never loses the live copy in memory. | `store.test.mjs` (quota test) |
| F-E6 | Test harness: a time-dependent invariant failed because it was checked at a different time from when the state was evaluated. A refused action also returned a ticked state, so "same state reference on refusal" was false. | Invariants are checked at the state's own evaluation time. A refused action returns the un-ticked input state. | `engine.fuzz.test.mjs` |
| F-E7 | Soak test: the simulated crew read prep times from the learned plan, so the plan fed on itself and drifted (a feedback loop). | The crew uses the starter prep times times a hidden speed factor, never the learned values. The sim owner must keep this rule. | `engine.soak.test.mjs` |
| F-E8 | Found by the comment pass: moving a hot batch that had already dropped below 135 F into cooling started a fresh 2-hour clock, so the time spent too cool was forgotten and the batch could take longer than 2 hours in total. | The cooling clock starts at the first low reading (`outSince`) when there was one, otherwise at the tap. This is the cautious rule and is consistent with F-E1. | `engine.unit.test.mjs` "cooling (F-E8)" |

| F-O1 | The original re-rendered the whole board every second. A tap that lands during the rebuild can hit a node that is about to be replaced and get lost. | Only the timer text and colour band update each second; the board itself re-renders when data changes. | `shell.e2e.mjs` (tap while ticking) |

## Metrics (src/js/40-metrics.js)

Spec ambiguities that had to be settled, plus defects found while building the analytics layer. The behaviour of every row is also written in `docs/metrics.md`.

| # | What went wrong | Fix | Test |
|---|---|---|---|
| F-M1 | SPEC 12 says plate sync measures "finished food waiting under the lamp" but not how. Spread (last done minus first done) and half the spread give the same number for two items and for evenly spaced three, so a first test passed with the wrong formula (found by mutation check: lamp = spread / 2 stayed green). | Lamp is the mean over all done items of (last done minus this item done). A test with uneven dones 100 / 120 / 220 s (lamp 73.3 s, spread 120 s) tells the two apart. | `metrics.test.mjs` plate sync, "lamp is a mean over ALL items" |
| F-M2 | The 12:45 am ticket: which date, which hour, which weekday? A calendar-day grouping would split one night across two days and put the late tickets on the wrong heatmap row. | Date, hour and weekday come from the **service date** of createdAt (day starts at 4 am). 12:45 am is hour 24.75 of the previous date, bucket 24, label "12 am"; 3:59 am is hour 27; 4:00 am starts a new day. | `metrics.test.mjs` service day rollover (4 tests) |
| F-M3 | Boundary values of the SLA bands were unspecified: is exactly 9:00 on time? | `totalMs >= warn` is warn and `>= breach` is breach (the worse level wins at the boundary). On time means strictly under warn. Unknown channels fall back to the first configured channel. | `metrics.test.mjs` SLA levels and boundaries; mutation of either `>=` goes red |
| F-M4 | Voided, forced and recalled tickets: SPEC 12 names them but not what each metric does with them. A forced bump has a real elapsed time, but its items were not all done, so plate sync and the critical-path split would be invented. | Voided tickets never enter speed stats and are counted as `voids`. Forced tickets stay in the speed stats but are flagged and left out of plate sync, anatomy and per-unit work times. A recalled ticket uses its latest `expeditedAt`; one that is active again is not finished. | `metrics.test.mjs` voided, forced and recalled tickets |
| F-M5 | The forced-bump test used a forced ticket with only one done item, so it was left out of plate sync anyway; deleting the `forced` check in the code left the suite green (found by mutation check). | The fixture ticket now has two done items and a pending one, so only the `forced` flag can keep it out. | `metrics.test.mjs` "forced bumps are counted and excluded from plate sync and anatomy" |
| F-M6 | A one-step item (no start tap) has no `startedAt`, so "response" and "work" were ambiguous and a zero-filled response would hide it. | Response is 0 and work is done minus fired for such items (as defined in the task); the four anatomy parts still sum exactly to the ticket total. | `metrics.test.mjs` ticket anatomy |
| F-M7 | Two percentage scales met: SPEC 7.7 gives yields as 0..100, while every share elsewhere is a fraction. Mixing them in one chart would be off by 100x. | All `*Pct` fields are fractions except `thermal().hotPct` / `chilledPct`, which keep the SPEC 0..100 scale (checked against `SB.engine.thermalYield`). `yieldComparison` returns fractions. Written in the header of `docs/metrics.md`. | `metrics.test.mjs` yield (thermal grid, engine agreement) |
| F-M8 | "Now" for lines still open (queueLoad) and for the live pace gauge: using the dataset range end made open lines run to a far-future end and shrank the last bucket's divisor to 1 ms. Reading the clock would break purity. | `opts.now` is explicit-only. Without it the newest timestamp in the data is used, never the range end and never the clock. The app passes the store clock. | `metrics.test.mjs` queueLoad (open lines run to now), live pace index |
| F-M9 | The `yield-misprice` insight spoke on an empty dataset (a thermal row always exists, so it compared the static yield with the model with nothing weighed). | Rule needs at least 3 weighed batches and a 5 % error; the "no batch weights" wording was removed. | `metrics.test.mjs` "yield-misprice ... needs 3 weighed batches", "silent on empty and thin data" |
| F-M10 | Insight wording: the plural helper made "batchs", and "between 12 to 1 pm" read wrongly. | Explicit plural form for batch / batches; a `hourBetween` helper builds "between 12 and 1 pm". | `metrics.test.mjs` waste and channel-gap insights |
| F-M11 | Calibration edge cases: should exactly 0.8 or 1.25 times the starter estimate count as drift, and should an item with 3 samples be flagged? | Exactly 0.8 or 1.25 is inside the band. Fewer than 5 samples (`opts.minSamples`) is "thin", never flagged, and sorts last. The insight additionally wants 8 samples. | `metrics.test.mjs` calibration |
| F-M12 | The undo rate has a denominator question: actions that were later undone are no longer in the event list (`reverted`) but they were still taps the crew made. | Kept-event lists drop reverted events, but the undo-rate denominator counts every `item_done`, `ticket_expedited`, `ticket_voided`, `batch_discard` and `sanitize_done` event including undone ones. | `metrics.test.mjs` line friction (2 / 14) |
| F-M13 | Sell-out clock: does a food-safety lockout count as selling out? It would blame the cook count for a thermometer. | Only `stock` and `manual` 86s count as sell-outs; safety lockouts have their own insight (`safety-lockouts`) and appear in `compliance().lockouts`. | `metrics.test.mjs` sellOutClock, safety-lockouts insight |
| F-M14 | `compare` with "Today" against "Yesterday" compares a part-day with a full day. Scaling the part-day would invent numbers. | No scaling: counts differ, medians stay fair; the limitation is stated in the docs and the first tile text says "previous period". Shares compare in points, counts are neutral (neither good nor bad). | `metrics.test.mjs` compare |
| F-M15 | Fixture builder used `delete` on optional keys, which put every fixture object in slow dictionary mode and made the 5000-ticket timing look 2x worse than the code is. | The builder copies only defined keys. | `metrics.test.mjs` performance |
| F-M16 | Performance of the first version: 230-400 ms cold for summary + byHour + heatmap + insights over 5000 tickets / 40000 events (budget 250 ms). | Typed-array sort for all statistics, one shared line model per call, event grouping that reads only the types that are asked for (42 ms down to about 5 ms), a cheaper finite-number check, and `M.prepare()` to share one pass across calls (about 115-145 ms cold). A single fused item loop was tried and reverted: it measured slower in an interleaved A/B run (166 vs 186 ms). The test judges the best of up to five attempts on fresh dataset copies, because the shared VM is noisy, and prints the first reading. | `metrics.test.mjs` performance (3 tests) |
| F-M17 | `prepare()` reuses the handle for the same dataset object. That is only safe if the dataset is not edited in place, which holds for `SB.store.dataset()` (copy-on-write states) but not for hand-built datasets in tests. | The cache checks the references and lengths of tickets / events / batches, settings, menu, ingredients, learned and the range, plus the options. `M.unprepare(ds)` clears it for in-place edits; the doc says so. | `metrics.test.mjs` "prepare(): one shared pass per dataset snapshot" |
